# 核心文档深化

## 目标

文档帮助维护者回答“为什么这样设计、边界在哪里、失败会怎样、修改后如何验证”。不要求建立固定的 core/dev/ref wiki 目录，优先使用仓库现有 `docs/` 结构。

## 审查维度

1. 事实：路径、符号、配置、命令和测试是否仍存在。
2. 动机：为何采用当前设计，替代方案和取舍是什么。
3. 边界：模块职责、依赖方向、输入输出和所有权范围。
4. 故障：超时、取消、错误、部分 I/O、关闭和资源耗尽如何表现。
5. 维护：哪些文件必须同步，哪些测试和审计验证变更。
6. 时效：历史计划、已完成 TODO 和已移除 API 是否清理。

## 写作规则

- 从源码和测试提炼结论，不把聊天记录当作证据。
- 代码片段只展示关键接口，避免复制大段会快速漂移的实现。
- 使用可点击的仓库相对路径和稳定符号名。
- 区分当前事实、计划、风险和待确认项。
- 删除空壳章节，不为完整目录留下无内容模板。

## 输出

先列高风险漂移和缺失，再给最小修订。需要新文档时说明位置、读者、维护责任和验证信号。
