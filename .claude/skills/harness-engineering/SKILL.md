# Harness Engineering

将代码仓库视为智能体的运行环境，而不仅是代码的存放处。人负责定义目标、取舍和验收标准；将可重复的知识、工具与反馈回路编码进仓库，使智能体能够执行和维护它们。

仅在实际项目中落实与当前目标相称的能力。不要为了“智能体优先”而重写稳定系统，也不要用一份巨型指令文件替代可定位的知识和自动检查。

## 评估与排序

1. 先阅读仓库现有的 `AGENTS.md`、贡献规范、架构文档、测试与 CI 配置；遵守已有本地约束。
2. 选取一个真实任务或近期失败作为探针，记录智能体在哪一步受阻：发现、实现、验证、评审、恢复或维护。
3. 将缺口转成最小的仓库内能力，而不是补一段临时提示。优先顺序是：
   - 让正确上下文可发现且保持版本化；
   - 让智能体能运行、观察并验证应用；
   - 让关键不变量可机械地检查；
   - 让反馈和常见修复回流为文档、测试或工具。
4. 为每项候选改进写明：当前证据、缺失能力、最小改动、验收信号和维护责任。优先处理同时降低人工介入和未来返工的项目。

读取 [references/principles.md](references/principles.md) 来校准评估维度、反模式和文章来源的设计依据。

## 生成仓库文档

先检查仓库；只记录能由代码、配置、现有文档或用户明确确认的信息。运行下列命令创建模板，默认保留现有文件：

```bash
python3 <skill-dir>/scripts/scaffold_harness_docs.py --target <repository-root>
```

模板位于 [assets/repository-docs](assets/repository-docs)。它会生成根级 `AGENTS.md`、`CLAUDE.md`、`ARCHITECTURE.md` 和 `docs/` 知识库。`CLAUDE.md` 只包含 `@AGENTS.md`，使同一组仓库指令可供 Claude Code 和 Codex 使用。

默认使用简体中文生成全部说明性文档。保留源代码标识符、文件路径、命令、配置键、协议字段和外部链接的原始形式；仅在用户明确要求或仓库已有的文档语言规范与此冲突时改用其他语言。

然后执行以下步骤：

1. 从项目清单、源码、测试、CI、部署配置和已有文档中填充模板；不要臆测架构、命令、所有者或安全控制。
2. 用具体的路径、命令和依赖方向替换所有 `TODO`；无法确认的内容标为待确认，并说明需要的证据。
3. 删除不适用于该仓库的可选文档，而不是留下空壳。例如无 UI 的项目不保留 `FRONTEND.md`。
4. 保持 `AGENTS.md` 为不超过约 100 行的导航入口；将细节沉入 `ARCHITECTURE.md` 和 `docs/`。
5. 运行仓库已有的文档、格式或链接检查；至少重新读取根级入口与索引，确认所有引用目标存在。

仅在用户明确要求时使用 `--force` 覆盖模板文件。生成完成后报告创建、保留、删除和仍待确认的文件。

## 构建仓库地图

保持根级 `AGENTS.md` 短小、稳定并可操作，将其作为目录而非百科全书。使其明确指出：

- 架构层次、领域边界和依赖方向；
- 产品规格、设计决策、活跃执行计划和已知技术债；
- 本地启动、测试、部署及故障排查入口；
- 项目约定、质量门和需要人工判断的升级条件。

需要兼容 Claude Code 时，创建或更新根级 `CLAUDE.md`，并使其内容仅为 `@AGENTS.md`。将全部共享指令保留在 `AGENTS.md`，不要在两个文件中复制规则。

将详细知识放入版本控制的结构化 `docs/` 或等价目录，并维护索引、所有权与交叉链接。让智能体从小的、任务相关的入口逐步展开上下文。不要依赖聊天记录、外部文档或隐性知识作为完成任务的必要前提。

## 闭合执行回路

为目标任务建立从更改到证据的短回路：

1. 使智能体可以在隔离环境或工作树中启动所需服务。
2. 提供可脚本化的验证：单元/集成测试、类型检查、构建、迁移检查和关键用户流程。
3. 让可观察性对智能体可查询：结构化日志、指标、追踪或清晰的本地诊断输出。
4. 对 UI 或端到端变更，提供可重复的浏览、快照或断言路径；使用事实证据确认修复。
5. 要求变更产出可审查证据，失败时先定位并补齐缺失能力，再重试。

避免把人工 QA 当作常规验证层。人工判断保留给产品取舍、风险接受和无法机械验证的结果。

## 编码约束与品味

在中央强制执行边界和不变量，在边界内部保留实现自由。将高频评审意见转成下列任一持久机制：

- 架构或结构测试；
- linter 规则及包含修复路径的诊断信息；
- 类型、模式和边界解析；
- 可复用工具、模板或脚手架；
- 明确的文档规则和验收测试。

偏好可组合、API 稳定、行为可在仓库内理解的依赖与抽象。为智能体提供可执行的约束，不要以主观的逐行实现指令取代结果约束。

## 交付与维护

将计划、决策、评审反馈和技术债作为版本化工件。每次完成后，判断是否暴露了重复缺口：若是，将其编码进文档、测试、工具或约束。

建立轻量、持续的清理循环，主动发现过时文档、架构漂移、重复实现和质量退化；让自动化任务提出小而可快速验证的修复。以持续偿还的方式控制熵，不要积累为大规模人工清理。

完成一次 harness 改进时，交付以下内容：

- 改进的能力及其所消除的人工步骤；
- 可重复运行的验证命令或可观察信号；
- 对仓库地图、规则或维护循环的相应更新；
- 仍需人工判断的边界与剩余风险。
