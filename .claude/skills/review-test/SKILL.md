# 测试覆盖审查

## 审查顺序

1. 读取变更涉及的生产入口、错误路径、状态机和资源所有权。
2. 找到现有单元、集成、互操作、性能和 contract 测试，确认它们实际覆盖的层次。
3. 按正常、非法输入、认证、网络故障、超时、取消、EOF、并发和重复关闭列出行为矩阵。
4. 检查测试是否真正驱动了异步任务，是否可能因没有 `ioc.run()`、未等待完成或异常丢失而假通过。
5. 判断缺失测试是单元测试、集成测试、互操作测试还是性能基线，不以增加任意覆盖率数字代替分析。

## 重点风险

- 只测 codec，不测 handler 到 outbound/tunnel 的集成行为。
- 只测成功握手，不测截断、错误认证、非法地址和上游失败。
- 测试使用 `poll()`、`run_for()` 或 sleep，掩盖协程启动和关闭竞态。
- 断言日志或实现细节，而不是稳定的协议行为。
- 测试留下 socket、timer、线程、子进程或 PMR resource。

## 输出格式

先列按严重程度排序的缺失项，并引用测试文件和生产入口；再说明覆盖假设、残余风险和建议测试。没有发现缺失时明确说明，并列出仍未验证的边界。

## 验证

使用当前 `tests/CMakeLists.txt` 的 test helper 和 `ctest` pattern。除非项目已有明确基线，不新增 80%/60% 等武断覆盖率门槛。
