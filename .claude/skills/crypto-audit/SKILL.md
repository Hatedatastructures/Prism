# 密码学审计

## 审计原则

先确定协议规范、现有实现和测试向量，再提出要求。HKDF salt、info、随机数来源、密钥长度和 nonce 规则不能凭通用口号强行统一，必须以具体协议和密钥生命周期为依据。

## 审计步骤

1. 画出输入密钥、派生密钥、salt、info、nonce、associated data 和输出的流向。
2. 核对 BoringSSL API、算法、密钥长度、nonce 长度、tag 长度和失败返回值。
3. 检查 nonce/计数器在同一密钥下不会重复，重置、移动、并发和重连不会破坏状态。
4. 检查认证失败发生在明文使用、目标拨号和状态修改之前。
5. 检查密钥、私钥和中间材料的存活时间、拷贝、日志和错误传播。
6. 对协议实现运行已有 golden vector、互操作和错误矩阵测试。

## 禁止未经证实的结论

- 不要求所有 HKDF salt 都随机或所有 info 都采用同一格式。
- 不用密码哈希替代协议规定的密码、UUID、PSK 或密钥派生流程。
- 不把固定算法、固定窗口或“浏览器行为”当作密码学正确性。
- 不记录密钥、明文认证材料或可重放的完整握手数据。

## 验证

报告必须引用协议规范、源码调用点或测试向量，区分算法错误、API 误用、密钥生命周期风险和部署配置风险。必要时调用 `replay-audit`、`leak-audit` 和 `dpi-audit`。
